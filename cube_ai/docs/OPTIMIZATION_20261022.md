# 2026-10-22 优化续报

## Problem

继续降低 Forge 实战的内存和等待时间，改善低费行动与终结手段的取舍，并修复已实现牌张被误判为不支持的问题。所有实验保留原始失败与跳过记录；没有用小样本胜率自动修改用户 Cube。

## Inputs

- 当前 Forge 2.0.15、已验证的模式说明兼容组件与本地卡牌快照。
- 原测速的固定牌组：双进程小范围比较 36 次原生运行，随后单进程持续检查 72 次，共 108 次，不计作新增学习样本。
- 两套事先冻结的 600 张 Cube，20 桌各比较两种组牌方式；计划 240 局，实际 216 局。
- 原引擎脚本声明的 182 个 UniversesWithin 正面替代名称，以及其中七个背面名称。

## Checks performed

### 较小内存的吞吐回收配置

新增 `parallel_small`：每个 JVM 的堆上限为 1536 MiB，使用 Parallel GC，处理器计数为 2，GC 线程为 1。它先只允许预览，不写入用户配置；通过固定用例检查后才加入正式测速选项。试验配置仍有禁止自动应用的通用保护。

相同牌组、随机种子与座位重复运行两次，逐局核对事件指纹、结果与实际后端。108 次全部正常，均为常驻原生入口，没有缓存复用、孤立进程回退或内存错误。持续检查包含跨过第 16 局的引擎退休与重建。

| 双进程配置 | 两次耗时中位数 | 引擎私有内存峰值 |
|---|---:|---:|
| 默认 GC，2048 MiB | 52.86 秒 | 1940 MiB |
| Parallel GC，2048 MiB | 47.48 秒 | 2484 MiB |
| Parallel GC，1536 MiB | 44.90 秒 | 2112 MiB |

相较本机此前采用的 Parallel GC 双进程配置，小堆版本耗时约少 5.4%，峰值私有内存约少 15%。这不是相较默认 GC 节省内存：默认双进程的峰值仍较低。单进程持续检查中，默认配置约 203.33 秒 / 1097 MiB，小堆 Parallel 约 194.69 秒 / 1249 MiB；均衡选择器在该单进程测试里仍推荐默认配置。

本机在核对原配置哈希与全部证据后采用小堆双进程配置。只登记实际测过的双进程并行数，不把四进程标为已验证。发布包不携带这台电脑的测速设置；其他电脑需自行测速。当前空闲内存不足时，自动模式仍会降低同时对局数。

测速还加强了实际后端检查：即使事件恰好相同，常驻引擎回退到另一入口的结果也不能支持自动采用新设置。暂停时间继续保留在原记录中，并从速度比较里排除。

### 延迟加载牌库：未采用

另外对原 Forge 的延迟加载偏好做了四次 ABBA 启动检查。启动约从 9.66 秒降至 1.66 秒，但私有内存没有达到事先要求的 20% 降幅，几乎不变；工作集减少不能替代该门槛。源码检查还发现部分全牌库遍历在延迟模式下可能只看到已加载集合。该设置未启用，也没有把启动收益宣传为实战加速。

### 保留终结牌的费用调整：未改默认

新实验方式保留原先选入的全部终结牌，只在其他咒语中调整低费与高费数量。每副牌的指挥官、颜色、地牌数及轮抓池保持不变；最多交换六个咒语。

两套冻结来源实际完成 216 局、36 桌完整配对，全部正常。四桌仅因 Sophina 被旧索引误判为不支持而跳过，原报告保留，未重开有利的包。

- 前四完整个人周期的零行动比例，配对平均下降 **4.32 个百分点**，整桌自助法描述性 95% 区间为下降 **2.01–6.71 个百分点**。
- 施放过终结牌的玩家比例平均下降 **1.54 个百分点**，区间为 **下降 5.56 至上升 2.47 个百分点**。
- 终结表现区间下界未达到预设的“不低于下降 5 个百分点”门槛，整体检查不通过。保留牌张不等于能及时施放它们。

默认继续优先单卡质量。界面提供“原均衡费用”和“保留已选终结牌”两个明确标注的实验对照，报告说明限制；不会自动修改当前 Cube。这个实验不能证明人类娱乐性或色组均衡。

### 原生同名替代牌索引与日志

Python 索引原先只读取脚本第一行 `Name:`，漏掉原 Forge 支持的 `Variant:UniversesWithin:FlavorName:`。例如 Sophina 对应脚本主名称 Chief Jim Hopper，实际 CardDb 可以找到它。正面索引现在仅在 JAR、牌张压缩包及完整系列数据指纹都匹配已验证清单时加入这些名称；存在本地松散脚本覆盖时不启用该清单。未知变体、Oracle 文本中提到的名称和背面不会被当作可单独选入的牌。

开发检查直接调用原 Forge 的 `CardDb.getCard`：182 个正面名称都能解析到脚本声明的原生牌及规则。不过 Forge 返回对象使用主名称，最初“返回对象名称必须等于请求名称”的严格检查为 **0/182**；这个失败记录保留。后续清单验证的是正确规则解析，不能声称 Forge 内部保留了替代名称。

导出牌组保留用户牌名，导入的已知主名称在本地牌库中归一；解析实战日志时，把主名称与已确认的背面名称映射回选入牌张，避免丢失实际施放和异能统计。没有模糊匹配或换成另一张功能相似的牌。清单固定哈希，缺失、篡改或运行时数据改变均停止启用；打包时缺失或篡改直接失败。

新增维护工具 `python -m cube_ai.tools.verify_card_names --compiler ECJ.jar --output 新目录`，以固定编译器校验值编译公开 Java 检查源，在独立工作目录查询原生数据库，不运行对局或 AI 服务。它保留请求、原始输出及清单；已有目录禁止覆盖。用已保存的原生查询结果重建清单，与发布的数据逐字段完全一致。

缓存实测：新索引冷构建约 0.96 秒，内存命中约 0.071 秒，重新进程内加载持久缓存约 0.084 秒。这个局部测量不代表整个应用启动时间。

原先跳过的四桌另做固定种子诊断，所有抓牌与选入牌组都与旧记录一致，原四桌没有补写。共十二局日志均正常结束；首局因本次私有测试脚本未建立记录目录，游戏结束后保存元数据失败，原“全部有后端元数据”门槛因此失败。保留该局日志且不重跑，修复测试脚本后只执行余下十一局；这十一局都有完整元数据，均为原生常驻入口，没有缓存或回退。四桌都能导出原牌名并运行，后十一局的日志正确归属了 18 次 Sophina 施放。这些诊断存放在学习语料目录之外，不作为额外训练或终结保护实验的补充样本。

源码完整回归 341 项通过。一次回归失败来自并行测试依赖机器实时可用内存：资源保护降至单进程后，测试仍断言存在两个进程的内部记录。该测试现为并行分支固定资源输入，生产的内存保护保持生效；原失败报告保留。名称清单损坏或缺失时，内存和磁盘索引缓存也会停止提供相关别名。

## Findings

较小 Parallel GC 堆在本机固定比较中同时改善了当前已采用配置的耗时与峰值内存。终结保护方案有前期行动收益，但未通过完整门槛；延迟加载也未通过门槛。卡名修复解决的是实际可用性及日志归属，并不是把未实现的牌标记为支持。

## Decision

- 正式提供小堆 Parallel 配置，由本机测速选择；不替其他电脑预装性能结论。
- 保留固定默认组牌策略，提供两个费用对照选项；不启用延迟牌库加载。
- 对完全匹配的原生数据启用经检查的正面替代名称，并保留严格打包检查与公开重建工具。

## Risks and limits

108 次重复运行来自固定牌组，不能穷尽长局、所有牌张或其他机器的内存需求。AI 对控制、组合技和多人政治的偏差仍存在。角色标签与协同密度仍是启发式；不能仅因某颜色在这一批机器人比赛中较强就自动削弱它。卡名清单随原生牌库绑定，升级引擎或系列数据后需重新检查。

## Next actions

四桌卡名实战诊断与源码回归已完成；继续做干净 Windows 便携验收，再发布新的独立版本。下一轮优先检查“资源生产者”和“收益牌”的角色误判，再设计不改变默认策略的构筑对照。
